# Commit Message

Use this skill to draft a commit message from the current git diff.

Default posture: **draft the message only**. Do not stage files or create a commit unless the user explicitly asks.

## Sensitive Content

1. Inspect changed filenames and the diff summary before reading file contents.
2. Treat authentication files, `.env` files, private keys, credential files, and secret files as sensitive.
3. If sensitive files are present, exclude their contents and request a redacted diff or a safe scope.
4. If a diff reveals a secret, stop inspecting that content and do not repeat the value.
5. Keep credentials, personal identifiers, and machine-specific paths out of commit messages.

## Diff Source

1. Prefer staged changes:
   ```bash
   git diff --cached --stat
   git diff --cached
   ```
2. If there are no staged changes, ask whether to use unstaged changes unless the user already said “unstaged”, “all”, or “current diff”.
   ```bash
   git diff --stat
   git diff
   ```
3. If the diff is large, inspect:
   ```bash
   git diff --cached --name-only
   git diff --cached --stat
   ```
   then read targeted hunks/files as needed.

## Message Style

Default to a conventional-style subject when it fits:

```text
<type>(optional-scope): <imperative summary>
```

Common types:

- `feat`: user-facing feature
- `fix`: bug fix
- `refactor`: behavior-preserving restructure
- `perf`: performance improvement
- `test`: tests only
- `docs`: docs only
- `chore`: tooling/maintenance
- `build`: build/dependency changes
- `ci`: CI changes

If conventional commits do not fit the repo style, use a concise imperative subject without a type.

## Quality Rules

- Subject line: imperative mood, no trailing period, ideally <= 72 chars.
- Body: include only when it adds useful context; wrap around 72 columns.
- Explain **why** when the diff alone does not make it obvious.
- Mention important follow-up or compatibility notes in the body, not the subject.
- Use a `BREAKING CHANGE:` footer only for actual breaking changes.
- Do not include “generated by AI” unless the user wants that.
- Do not mention tests unless the user asks or the commit body needs validation context.

## Output

When the user asks for one message, output only the commit message in a fenced `text` block:

```text
feat(folders): add expandable project tree

Introduce a shared tree builder for nested project folders and wire the
folders view to render visible rows based on expansion state.
```

When the change could reasonably use different scopes/types, provide 2-3 options and briefly explain the tradeoff.

## If Committing Is Requested

Before running `git commit`:

1. Confirm which files are staged.
2. If staging is needed, ask before `git add` unless the user explicitly asked to stage all.
3. Show the final message.
4. Commit with a file-based message (`git commit -F <file>`) for multi-line messages.
